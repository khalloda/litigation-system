All four passwords are configured; no password or hash was inspected or reported.

Current identity properties:

- `user_accounts.person_id → people.id` uses `ON UPDATE CASCADE, ON DELETE RESTRICT`.
- No `system_migration` account or person exists.
- `created_by` and `updated_by` currently point to nothing formally.
- Account disabling invalidates sessions and clears lockout state.
- Person inactivity prevents login.
- D25 requires account/staff removal to mean disable/deactivate, not deletion.
- Current database constraints do not independently prohibit deleting a `user_accounts` row.
- Session claims contain account ID, person ID, username, display name, role, session version, login time, and absolute expiry.
- They do **not** contain an immutable audit-session identifier.
- Roles are refreshed from the database when sessions are validated, which is good; the event must snapshot the role actually effective at event time.

Recommended identity model:

- Add an immutable `audit_actor` registry.
- One actor per `user_accounts` row, linked by stable account ID.
- One non-login special actor with identifier `system_migration`.
- Existing and future `created_by`/`updated_by` columns reference `audit_actor.id`.
- Actor and event foreign keys use `ON UPDATE RESTRICT, ON DELETE RESTRICT`.
- Disabling, renaming, or changing the role of an account never rewrites historical events.
- Events separately snapshot username/display name and role at event time.

This avoids inventing a fifth application role or pretending a machine actor is a human `people` row.

## 6. Write paths and spoofing analysis

| Path | Current writes | Authorization position | Attribution/event state |
|---|---|---|---|
| `authenticateCredentials()` | Failed-attempt count, lockout, successful-login timestamp | Public credentials workflow | No actor, IP, UA, session ID, or event |
| `changeOwnPassword()` | Hash, password time, forced-change flag, session version, lockout reset | Session validated before write | No `updated_by`; no password-change event |
| `setApprovedAccountPassword()` / `auth:set-password` | Password initialization/reset and session invalidation | Local interactive command, not a web session | Operator is not recorded |
| `user_accounts_sync_person_login` trigger | Updates `people.can_login` and `updated_at` | Nested DB consequence | Leaves `people.updated_by` null |
| Future permission wrappers | Authorize before protected handler/action runs | Correct and fail-closed | Good injection point for an audit context, but no such context exists |
| Prisma `@updatedAt` | Maintains `updated_at` only for Prisma updates | Application layer only | Direct SQL bypasses it |
| Migration/transform scripts | Staging load, transforms, review imports, backfills, evidence | Local trusted maintenance paths | No actor context; no event trail |
| 52 immutable migrations | Direct SQL/DDL/DML | Privileged database operation | No event trail |
| Disposable fixtures | Direct SQL and Prisma mutations | Fixture databases only | Demonstrate present gaps |

Important findings:

- No business CRUD screen or route exists yet. This is the best time to establish the audit contract.
- A direct insert or update may currently supply any integer, including `999`, as an actor. Existing fixtures deliberately demonstrate that and still pass.
- There is no actor FK or validation trigger.
- A caller can omit actor fields.
- A direct SQL update can omit `updated_at`.
- User-supplied roles are correctly ignored for authorization, but no equivalent protection exists for actor IDs.
- There is no transaction/session/request audit context.
- No current event table, event trigger, or semantic audit API exists.
- Seven catalog triggers containing the word “audit” are migration-evidence guards, not an application audit trail.

## 7. Architecture evaluation and recommendation

| Option | Advantages | Material weaknesses | Estimated implementation |
|---|---|---|---|
| Explicit `createdBy`/`updatedBy` in every Prisma call | Simple and typed; minimal DB logic | Easy to omit or spoof; misses direct SQL and nested trigger writes; weak event coverage | 3–5 days, but incomplete |
| Application writes every event explicitly | Best semantic names and redaction control | A forgotten path silently creates a gap; direct SQL and trigger consequences are missed | 5–8 days, but incomplete alone |
| PostgreSQL triggers with transaction-local context | Central, atomic, covers Prisma/direct SQL/nested writes; can reject missing context | Does not by itself understand login/report/download semantics; requires careful transaction discipline | 7–12 days |
| External CDC/logical-decoding service | Captures all row changes without application integration | Additional infrastructure; weak user/request context; harder redaction; unnecessary at this scale | 2–4 weeks plus operations |
| **Hybrid: local context + triggers + explicit semantic events** | **Complete attribution, atomic before/after events, semantic non-row events, fail-closed enforcement** | More initial engineering and fixture work | **10–16 development days total** |

### Recommended flow

```text
Authenticate and authorize
        ↓
Build trusted AuditContext from the validated session/request
        ↓
Start Prisma interactive transaction
        ↓
set_config(..., true) for transaction-local actor/request metadata
        ↓
Application writes
        ↓
DB triggers set actor/timestamps and append redacted row events
        ↓
Application records semantic events such as login/report/export/download
        ↓
Commit atomically
```

Required properties:

- Use `set_config(..., true)` only inside the same interactive transaction as the writes.
- Never use session-level `SET`; pooled connections could leak one user’s identity into another request.
- Pass the transaction client into services; do not write through the global Prisma client inside an audited transaction.
- The trigger overwrites or rejects caller-supplied actor/timestamp values.
- Missing or invalid actor context fails closed for future application writes.
- System/migration tools supply an explicitly validated system context.
- Row triggers cover nested updates such as `user_accounts → people`.
- Semantic events cover actions with no row transition, including unknown-user login failures and report execution.
- Generate a separate random audit-session UUID. Do not store the Auth.js JWT/cookie or any bearer token.
- Capture role as an immutable event snapshot.

### Database-role consequence

The application currently connects as `litigation`, which is a PostgreSQL superuser and owns all project tables. A superuser/table owner can defeat grants, triggers, and append-only protections.

Meaningful append-only enforcement therefore requires:

- A migration/administration principal retaining ownership.
- A separate non-superuser application login with only necessary DML/SELECT rights.
- No direct application `UPDATE`, `DELETE`, or `TRUNCATE` privilege on audit events.
- Narrow security-definer functions with fixed `search_path` where the runtime needs to append semantic events.
- Separate migration and application connection settings; no secrets committed.

No extra container, hosted service, plugin, or license is needed.

## 8. Truthful historical backfill

Recommended backfill semantics:

| Current row class | `created_by` | `updated_by` | Reason |
|---|---|---|---|
| Migrated targets, junctions, lookup seeds, current logos | `system_migration` | `system_migration` | Repository history proves their creation/current state was produced by migration/transform work; no business CRUD exists yet |
| Existing `people` rows, including two Task 3.1 native identities | `system_migration` | `system_migration` | All current creation and changes are migration-defined |
| `person_name_alias` | Add missing columns; use `system_migration`; set initial `updated_at = created_at` | `system_migration` | No later human edit evidence exists |
| `user_accounts` | `system_migration` | **NULL / historical actor unknown** | Accounts were created in migration, but later password setup, login, or failed-attempt updates cannot be assigned truthfully to a known operator |
| Staging/quarantine/evidence | No retrofit | Existing provenance model | These are evidence, not application activity rows |
| Future application-created rows | Authenticated actor required | Authenticated actor required | Trigger-enforced |
| Future trusted migration/seed rows | Explicit system actor | Explicit system actor | Context must identify the exact trusted process |

Four existing `user_accounts.updated_by` values should remain null. “Populated everywhere” must be refined to permit documented historical unknowns rather than fabricating an actor.

Other rules:

- Do not rewrite `created_at` to a source business date.
- Preserve `admin_tasks.task_created_date` as the one explicit legacy creation-date field.
- Do not reconstruct historical logins, password changes, or report executions.
- Do not fabricate 45,000 historical “create” events.
- Record one system-level `audit_baseline_established` event containing counts and protected digests, then begin the event trail from the actual deployment time.
- Entity history can state that the record was migrated and earlier Access change history was unavailable.

### Protected-state complication

At least **5,209 migrated billing/attendance rows** reject ordinary updates through existing immutability triggers:

- 543 invoices
- 597 payments
- 47 allocations
- 4,022 attendance rows

The backfill must not permanently disable those guards.

Safe approach:

1. In the new transaction, temporarily replace the exact guard functions with a migration-only exception that permits changes only to actor columns.
2. Backfill actor IDs without changing business fields or timestamps.
3. Restore the exact strict function definitions before commit.
4. Let the transaction roll back everything if any assertion fails.

Several protected digests serialize whole target rows and currently include null actor keys. Preserve their historical values by canonicalizing actor fields back to JSON null inside the legacy digest calculation, while adding a separate permanent audit-attribution digest. This retains the old business/timestamp baselines rather than silently blessing new baselines.

The client-logo reconciliation also currently treats `updated_by IS NULL` as evidence that a logo is still the original import. It must recognize `system_migration` explicitly instead of using null as a surrogate actor.

## 10. Security, privacy, and retention

Recommended event fields include:

- Stable event ID and occurrence timestamp.
- Actor-registry ID, stable actor identifier, username/display snapshot, and role snapshot.
- Action and outcome.
- Entity schema/table and structured primary key.
- Redacted changed-field list and bounded before/after JSON.
- Request/correlation ID.
- Non-secret audit-session UUID.
- IP address using PostgreSQL `inet`.
- Bounded raw user agent and optional locally derived device classification.
- Report/export/download identifiers and redacted parameters.
- Migration/version metadata for trusted system events.

Security requirements:

- `created_at`, `created_by`, event timestamp, actor, role snapshot, request ID, and session ID are immutable.
- Do not dump complete rows indiscriminately.
- Exclude `password_hash`, password fields, tokens, cookies, `AUTH_SECRET`, database URLs, raw binaries, and immutable `legacy_source_payload` fields.
- Use per-table allowlists for auditable fields.
- Bound JSON and user-agent sizes.
- Store relationship IDs and changed relation facts, not redundant entire parent records.
- Parse forwarding headers only behind an explicitly trusted reverse proxy; otherwise an attacker can spoof IP addresses.
- Unknown-user login failures have no actor FK but retain a bounded attempted username and request metadata.
- Password changes log the fact and actor, never the old/new hash or password.
- D25 archive/restore events must be semantic actions, not generic updates.
- Ordinary administrators must never be able to edit or delete audit events through the application.
- The migration/superuser principal remains an operational trust boundary.

Retention is resolved by **D32**:

- Retain audit events indefinitely.
- No automatic deletion, rolling expiration or purge.
- No application role may update, delete or truncate events.
- Account disablement and record archive/restore never remove history.
- Routine retention deletion therefore cannot defeat a legal hold.
- Any future change requires a new explicit owner decision and must itself leave
  durable audit evidence.
