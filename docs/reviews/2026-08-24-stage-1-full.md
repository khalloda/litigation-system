# Stage 1 review — tasks 1.2c through 1.6

VERDICT: fix these first

## MUST FIX (4 items)

- **The financial protections are incomplete, and the existing ones are not watched by `db:check`.** The live database has four correct checks covering the main invoice amount, payment credit/debit and an allocation's 0–1 share. However, [`scripts/check-db.ts`](../../scripts/check-db.ts#L693) never verifies that any of those four constraints still exists, so all 31 checks would remain green if they were dropped. Two later money columns, `invoices.amount_usd` and `invoices.receipt_amount`, have no non-negative protection at all even though the migration states that money in this system cannot be negative. In real life, a bad import could reduce an invoice or receipt total with a minus sign and no guard would object. Add non-negative constraints for those two columns and make the standing check verify the exact table, validated constraint and rule for all six. **Cost: about 2–3 hours.**

- **Most database-only guards are checked by name, not by what they do.** The live definitions are right today, but [`db:check`](../../scripts/check-db.ts#L677) accepts the three junction checks and one-lead index solely by object name; the one-primary index is handled the same way, and the seven Arabic triggers are counted by name without checking their table, enabled state, event, function or column arguments. Dropping one is caught, but replacing it with a harmless rule carrying the same name is not. A non-unique or wrongly filtered “one lead” index, a `CHECK (true)`, or a disabled normalising trigger could therefore leave the report green. Verify the catalogue definitions, not just names, and add a data-level check for matters that already have more than one lead. **Cost: about 3–5 hours.**

- **The standing Arabic guard does not cover all the fields and negative cases it claims to protect.** The live normaliser currently keeps all four required pairs distinct, including `أول درجة` and `ابتدائي`. But [`db:check`](../../scripts/check-db.ts#L760) contains only the other three negative tests. Its drift query also checks only five of the seven shadow columns, omitting `clients.full_name_normalised` and `matters.subject_normalised`. If either of those triggers were disabled or misdirected before Stage 2, names or matter subjects could become unfindable while every check stayed green. Add the fourth negative test and both missing shadow comparisons; combine this with the exact trigger checks above. **Cost: about 45–90 minutes.**

- **The invoice-share assertion passes incomplete allocations.** It uses `sum(share) <> 1`, but PostgreSQL ignores null shares. In a read-only in-memory test, one allocation of `1.0` plus another with no share produced a total of `1` and zero failures. Rows with a null `invoice_id` are also grouped together, so shares belonging to different unresolved invoices can accidentally total 1. In real life, a partner's allocation could be missing while the financial check says it is complete. Fail null shares explicitly, calculate totals only for resolved invoices, and report unresolved parents through the quarantine assertion rather than combining them. **Cost: about 1–2 hours.**

## SHOULD FIX (4 items)

- **`J` is folded everywhere, not only in the case-year suffix specified by the PRD.** The current function makes `JTI` and `قTI` identical. That is correct for `140J` versus `140ق`, but not for ordinary Latin text in a client name or matter subject. It can produce unrelated search results. Restrict this fold to the documented case-number context and add a negative test for ordinary Latin `J`. **Cost: about 1–2 hours.**

- **The 15 approved client branches are correct now, but the standing check does not protect the full set.** The live list matches the firm's 15 values exactly; every one of the 16 removed values has its crosswalk, and the old `جنح → الجنح → جنح` chain now points directly to `matter_category/جنح`. The crosswalk baseline protects those mappings. However, the branch check names only `المنطقة الحرة` and the 16 forbidden values. Replacing any of the other 14 approved branches with a new value would keep the count at 15 and still pass. Protect the initial 15 as a reviewed baseline while still allowing later deliberate additions. **Cost: about 30–60 minutes.**

- **The eleven billing lookup rows have no standing content check.** They currently match `sql/billing-lookups.sql` exactly—5 statuses, 2 invoice types and 4 lawyer-share roles, with all Arabic labels still empty. `db:check` only proves that the three tables exist. A deleted or changed code, or an invented Arabic legal/financial label, would not be reported despite `TASKS.md` saying it is asserted. Add exact seed checks or a reviewed baseline. **Cost: about 30–60 minutes.**

- **The authoritative documentation still contains several superseded facts.** [`docs/DATA-MODEL.md`](../DATA-MODEL.md#L281) says invoices link by `client_id`, although D3 and the schema correctly link them through `fee_letter_id`; its deferred attendance summary still says `date/status` instead of `attendance_date/situation`. It also promises a GIN index for every searchable shadow column while `clients.full_name_normalised` is the seventh shadow and has no index. [`schema.prisma`](../../prisma/schema.prisma#L1536) still says the billing column lists are incomplete, and its fee-letter junction comment says 289 unmatched values out of only 288. These do not damage today's database, but they can send the Stage 2 loader in the wrong direction. Reconcile the comments with the settled schema, or document why the seventh search field is intentionally unindexed. **Cost: about 20–40 minutes.**
