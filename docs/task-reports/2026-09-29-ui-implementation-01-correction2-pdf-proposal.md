# R4 — bounded diagnosis and next proposal

Status: BLOCKED. No production PDF or dependency change is proposed as a demonstrated fix.

Twenty fresh synthetic outputs use the exact bundled Noto Sans Arabic Regular font, pinned Playwright 1.62.1 and two already-installed executables: locked Chromium 151.0.7922.34 and Chrome 153.0.8010.53. Each output is bound to its source HTML, expected codepoints, font and executable hashes, browser version, options and actual platform-font result. No owner data, application requests, PDF-viewer route or installation was involved. Chrome 153 was a controlled comparison only; the application remains locked to its existing renderer.

Under installed PyMuPDF 1.28.0, Latin `HP 1061/52` and the single Arabic letter `ق` pass exact text and search in both engines. All eight more complex cases fail: an Arabic word, hamza word, marked word, phrase, mixed case identifier, Latin company token in Arabic, multiline cell and table boundary. Table output includes a second HP cell: whole-document equality is not treated as cell equality. Exact target substring/search also fail. Generated PDFs and complete raw outputs are retained under pdf-isolation. No text normalization was used.

For locked Chromium, default extraction of `إبراهيم` inserts spaces: `إ براه يم`. Disabling only the decoder's inferred-space insertion yields that word correctly, but `ثانٍ`, `قضية` and the mixed case identifier still have ordering/line-grouping problems. This alternate decoder setting is diagnosis, not a fix or revised acceptance gate. Native ActualText clusters and ReversedChars markers are present; the marked word contains runs in visual order. Individual ActualText runs need not contain every single-glyph character, because ordinary glyph-to-Unicode mapping also contributes. The observations do not prove the font alone, Chromium alone or every viewer is faulty.

Two first-page images (locked hamza and diacritic) were visually inspected with the offline renderer: letters/marks are visible and connected. That observation does not prove exact copying. The retained Acrobat Pro 2022.003.20282 copy failure remains valid; the possible separate row-index `1` is not itself counted as data-cell corruption. The same old sample was not sent back for another owner check. The failed reviewer marked-content experiment is preserved and was not applied to production or repeated.

No proven replacement/fixed version is known.
